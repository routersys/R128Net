Jan Kokemüller氏によるEBU R128およびITU-R BS.1770準拠のラウドネス測定ライブラリ[libebur128](https://github.com/jiixyj/libebur128)をC#へ完全移植したライブラリです。
測定はマネージドヒープを一切確保せずに動作するため、解析の経路にガベージコレクタが関与しません。
状態は単一のネイティブ領域から供給し、主要な演算はunsafeなポインタで記述し、ライブラリ全体をNative AOT向けに注釈しています。
正しさは、ソースを読むことではなく、MSVCでビルドした原典Cが出力した基準データとの比較で確認しています。

## 概要

R128Netはlibebur128をC#へ移植したものです。瞬時ラウドネス、短期ラウドネス、統合ラウドネス、ラウドネスレンジ、相対閾値、サンプルピーク、トゥルーピークの全てを提供し、ヒストグラムアルゴリズムと、複数の測定インスタンスを一つの値へ集約する機能も備えます。

公開APIはモダンなC#の書き方です。音声は`ReadOnlySpan<short>`と`ReadOnlySpan<int>`と`ReadOnlySpan<float>`と`ReadOnlySpan<double>`で受け渡します。モードの集合は、原典の含意関係を再現する`[Flags]`列挙型です。オプションは`init`アクセサを持つ`readonly record struct`で、結果は単一の`LoudnessMeter`クラスのプロパティから読み出します。ポインタを使う内部の実装は公開しません。

状態は全て、生成時に`NativeMemory.AlignedAlloc`で確保する、64バイト境界に揃えた単一の領域から供給します。その領域の配置は、専用の型の`Layout`メソッドに一度だけ記述します。ソースジェネレータがその署名を読み、必要量の照会と束縛の両方を生成するため、報告する必要量と実際の消費量が食い違いません。

原典のCは本リポジトリに同梱していません。`reference`配下の参照ハーネスは、libebur128を固定したコミットで取得してMSVCでビルドし、各段の内部状態を倍精度のまま書き出します。テストはその出力を読み込み、C#側の結果と比べます。

## 導入方法

```sh
dotnet add package R128Net
```

1. チャネル数と標本化周波数と必要なモードを指定して`LoudnessMeter`を生成します。モードごとに処理時間を要するため、必要最小限の集合を指定してください。
2. インターリーブされた音声を`AddFrames`へ投入します。フレーム単位で割り切れる限り、任意の長さのバッファを受け付けます。
3. 結果はプロパティとして読み出します。測定の途中でも読み出せます。
4. テストが突き合わせる参照データは`reference/data`にコミットしてあるため、クローンした直後からテストを実行できます。作り直す場合は`reference/build.bat`を実行してください。libebur128を取得してMSVCでビルドし、ダンプを上書きします。
5. 実行例のNative AOTバイナリを作る場合は`publish-aot.bat`を実行してください。

## 主な機能

### 1. ラウドネスの測定

BS.1770の前置フィルタは高域シェルビングと高域通過の縦続接続であり、原典と同じく単一の4次系へまとめて実装しています。ゲーティングブロックは400msの長さを100msずつ進めるため、2011年改訂が定める75パーセントの重複となります。

瞬時ラウドネスは直近400msを、短期ラウドネスは直近3秒を対象とします。統合ラウドネスは-70 LUFSの絶対ゲートを適用した後、ゲート前の平均から10 LU下の相対ゲートを適用します。ラウドネスレンジはEBU Tech 3342に従い、平均から20 dB下のゲートを通過した短期ブロックの第10百分位数と第95百分位数を取ります。`GetLoudnessOverWindow`は設定した最大窓までの任意の窓のラウドネスを返します。

### 2. ピークの測定

サンプルピークは、絶対値が最大の標本を入力形式の全振幅値で除した値です。トゥルーピークは、96 kHz未満では4倍、192 kHz未満では2倍に過標本化します。過標本化には49タップの多相FIR補間器を使います。192 kHz以上では信号をそのまま扱います。いずれも、測定全体に対する値と、直近の`AddFrames`に対する値を取得できます。

原典は、変換した入力を一つ目のバッファへ書き、補間した標本を全て二つ目のバッファへ書いたうえで、そのバッファを別の走査でたどってピークを求めます。本実装は、この二つのバッファと二回の走査を一つの処理にまとめて取り除いています。格納した値は変わらずに読み戻されるだけで、最大値は走査の順序に依存しないため、まとめても全ての結果が同一です。

### 3. ゲーティングとヒストグラム

チャネルの重みはBS.1770に従います。サラウンドの位置は1.41倍、デュアルモノとして指定したチャネルは2倍の重みで寄与します。未使用として指定したチャネルは、処理を飛ばし、環状バッファへも書き込みません。

ヒストグラムアルゴリズムは、ブロックのエネルギーを0.1 LU刻みの1000個のビンへ量子化するもので、`LoudnessModes.Histogram`で選択します。結果が量子化される代わりに、長時間の測定でも記憶域に上限ができます。指定しない場合は、ブロックのエネルギーを個別に保持します。これが既定の動作で、原典と一致します。

### 4. 複数インスタンスの集約

`LoudnessMeter.GatedLoudness`と`LoudnessMeter.LoudnessRangeOf`は測定器の並びを受け取り、全ての素材を単一の測定器へ投入した場合と同じ値を返します。複数のファイルを一つの番組として測定する場合や、一つのファイルを複数のスレッドで測定する場合に用います。ヒストグラムアルゴリズムを使うかどうかは、全ての測定器で一致している必要があります。

### 5. 無確保と状態領域

フィルタ後の環状バッファ、フィルタ状態、チャネル配置、ピークの配列、ヒストグラム、補間器の全てが、生成時に確保する、整列済みの単一のネイティブ領域に置かれます。`[StateLayout]`を付けた型では、必要量を、確保子を型引数に取るジェネリックな`Layout`メソッドに一度だけ記述します。計測用の確保子で実行すると、記憶域に触れずに必要バイト数が求まります。束縛用の確保子で実行すると、実際の割り当てが行われます。ソースジェネレータは、この単一の署名から`GetRequiredBytes`と`Bind`を生成します。

ブロックエネルギーの履歴は、既定ではネイティブ領域上で倍々に伸び、原典の実質的に無制限な履歴を再現します。`PreallocateHistory`を指定すると、要求した最大履歴から、履歴とラウドネスレンジが整列に使う領域の寸法を一度だけ決めます。これにより、以後は単一の測定器に対する測定も問い合わせも、確保を一切行いません。複数の測定器に対する`LoudnessMeter.LoudnessRangeOf`は、全ての測定器のブロックを先頭の測定器の領域へ集めて並べ替えます。そのため、合計の個数がその測定器の確保した量を超えるときに一度だけネイティブ領域を確保し、以後の問い合わせのために大きい領域を保ちます。

`Reset`は、チャネル配置と窓と履歴を保ったまま、測定の状態を生成直後へ戻します。複数の候補を続けて測定する場合、生成の費用は候補ごとではなく一度で済みます。測定器の再利用には`Reset`を使います。

マネージドヒープを確保しないことは、主張ではなく計測で示しています。`GC.GetAllocatedBytesForCurrentThread`で測ると、4種の入力形式の`AddFrames`と、ラウドネスレンジが行う整列を含む全ての問い合わせのいずれでも、差分は0バイトです。

### 6. 数値検証

テストでは、MSVCでビルドした原典Cが出力したデータと比べます。libebur128の内部状態は不完全型であるため、ハーネスは`ebur128.c`を自身の翻訳単位へ取り込み、状態へ直接アクセスします。テストが要求する一致の水準は次のとおりです。

| 段階 | 一致 |
|---|---|
| 前置フィルタの係数、20種の標本化周波数 | ビット単位で一致 |
| フィルタ出力とフィルタ状態 | ビット単位で一致 |
| 無音時の減衰におけるフィルタ状態、40ブロック分 | ビット単位で一致 |
| 補間器の係数、2種の過標本化率 | ビット単位で一致 |
| ゲーティングブロックと短期ブロックのエネルギー | ビット単位で一致 |
| 統合ラウドネス、瞬時値、短期値、任意窓、相対閾値 | ビット単位で一致 |
| ラウドネスレンジ、履歴を個別に保持する方式とヒストグラムアルゴリズムの両方 | ビット単位で一致 |
| サンプルピークとトゥルーピーク、全体と直近の両方 | ビット単位で一致 |
| ヒストグラムのビン計数、各1000ビン | ビット単位で一致 |
| 3インスタンスにわたる集約 | ビット単位で一致 |

これらの一致は、次の8種の構成で成り立ちます。ステレオ、5チャネルサラウンド、デュアルモノ、ヒストグラムアルゴリズム、100ms境界に揃えたバッファ長と揃えないバッファ長、44100 Hz、96000 Hz、そして振幅が1e-310と1e-40と5e-324と厳密なゼロを巡回する敵対的な信号です。

超越関数は個別に計測しています。`Math.Tan`と`Math.Log`は、それぞれ20000点の標本で、MSVCのランタイムと厳密に同じ倍精度値を返します。`Math.Pow`は、標本の千分の一未満で最終位が1だけ異なるため、ヒストグラムの境界表は実行時に計算せず埋め込んでいます。

テストは274件あり、その全てが通ります。原典との比較に加えて、全ての公開メンバの解放済み検査とモード要求、全ての引数の検証、消去した測定器が生成直後の測定器と上記の全構成で同一の結果を出すこと、そして全ての高速経路が単純な参照実装と一致することを検証しています。

|---|---|
| 遅延線を拡張済みの倍精度で保持し、タップごとの変換を除去 | 1.5倍 |
| 補間器のタップの積と和から、恒等となるフラッシュを除去 | トゥルーピークで1.4倍 |

| スカラーのサンプルピークで絶対値を分岐なしに計算 | 6チャネルのサンプルピークのモードで3.0倍 |

最初の行は作業の初期に計測した値です。残りは、各変更の直前のコミットと1件ずつ、Native AOTで両者を交互に走らせ、上記のとおりプロセスを固定して計測しました。値は13回から21回のうち最良の値の比です。同じビルドの2本の間にも、段によって最大で約10パーセントの差が出たため、小さい比にはその不確かさがあります。

全体では、Native AOTで最適化前の移植と現行の移植の差は、2チャネルの全モードで8.8倍、既定の配置の6チャネルで8.9倍、1チャネルで5.9倍です。実行時コンパイルでは、初回の呼び出しのコンパイルを含めて、同じ比較が6.8倍、9.1倍、5.4倍でした。計測した全ての構成で、出力はビット単位で一致しています。

密な補間の以前の構造は、遅延線を2倍長に複製し、2フレームを展開し、3つの位相を1本のベクトルのレーンに保持するものでしたが、連続した4フレームをレーンに載せる構造に置き換えました。副フィルタが密にならない標本化周波数を担当する汎用の経路は、2倍長の遅延線を保っています。

補間器のタップのフラッシュが恒等になることは、次のように正確に示せます。履歴に入るのは、各標本を単精度へ丸めてそこで先にフラッシュするため、零か絶対値が2^-126以上の値だけです。補間器が残す係数はどれも10^-6を上回ります。したがって積は全て2^-146以上です。部分和は2^-198の整数倍なので、零でない部分和は全て2^-198以上であり、倍精度の最小正規数2^-1022を大きく上回ります。単精度への丸めとフラッシュはどちらも単調なので、複数の大きさの最大値は、個々に丸めずに1回だけ丸めても同じです。そのためピークは倍精度で保持し、呼び出しごとに1回だけ変換します。

各蓄積の連鎖は原典の加算順序を保つ必要があるため、連鎖そのものは短縮できません。速くなった理由は、独立な出力を並べて計算することにあります。1フレームの3つの位相が空きレーンのあるベクトルを共有しなくなり、4フレームが一緒に進みます。

補間器は、倍精度の計算の大半を証明によって避けます。各出力は履歴の標本と係数の積12個の和で、履歴には単精度の値を倍精度へ拡幅したものが入っています。8フレームを一度に扱い、3つの位相それぞれの中央の4タップを単精度で足します。残りの8タップは、係数の絶対値の和に、8フレームが読む20個の標本の最大の大きさを掛けた値で押さえます。さらに、その最大の大きさの2x10^-5の余裕を加えます。単精度の和の丸め誤差はその約10^-6以下なので、余裕は必要な量の20倍あります。この余裕は、倍精度の結果の丸め誤差と、スレッドが非正規化数のフラッシュを有効にしている場合の誤差も覆います。8フレームの全ての出力（中央の標本そのものを含む）の上限が、それまでに見た最大の出力と、以前の呼び出しが残したピークのどちらか大きい方の0.99999倍以下なら、どの出力も最大値を変えられないため、8フレームの厳密な計算を飛ばします。出力がその最大値を超えるのはまれなので、判定は、一様な雑音のブロックの99.5パーセント、音楽的な信号の98.8パーセント、クリップした雑音の97パーセントで通りました。全て0の窓は、出力が厳密に0になるので、そのまま通します。通らなかったブロックは、変更のない厳密な経路で計算するため、結果は判定が通る頻度に依存しません。

判定の健全性は、最終の結果ではなく直接試験します。最終の結果は単精度へ丸められるため、その分解能より小さい超過は隠れてしまうからです。形の異なる数十万個の窓（雑音、孤立したスパイク、正弦波、出力を最大にする符号の並び、定数、非数や無限大を含む窓、非正規化数、10^-35から3x10^38にわたる大きさ）について、真の最大の出力の1パーセント下からはるかに上までのしきい値で判定を実行し、最大の出力がしきい値を超えるときに判定が通らないことを確かめます。意図的に壊した版（全ての余裕を同時に外したもの、半分にした尾部の上限、最も古い標本や最も新しい標本を見落とす窓、検査しない中央の標本、1を超えるしきい値の倍率）のそれぞれで、この試験は失敗します。

密な補間は、128ビットのベクトルがハードウェアで使えるプロセッサー全てで使います。ARM64やAVX2のないx64のように256ビットのベクトルが使えない環境では、ランタイムが256ビットの演算を128ビットの2つに分割します。GitHub Actionsのランナーで実行時コンパイルのとき、実行例は、Windows ARM64とLinux ARM64で全モードが113 msから43 ms、`DOTNET_EnableAVX2=0`のx64で62 msから22 msになりました。ハードウェアのベクトルが全くない場合（`DOTNET_EnableHWIntrinsic=0`）は、同じコードがスカラーの経路よりずっと遅く、160 msに対して940 msになるため、そこでは汎用の経路を保っています。

入力から履歴への変換は、1チャネルと2チャネルで8標本ずつ行い、2チャネルではインターリーブされた左右をシャッフルで分けます。16ビットと32ビットの整数は厳密に変換します。2のべき乗の倍率は単精度への丸めと可換なので、ベクトルの結果はスカラーの定義とビット単位で一致します。違うのは、シグナリング非数のペイロードだけです。演算が静かな非数に変えるため、最大値に影響しません。

K特性フィルタには、入力と4つの状態がいずれも零か絶対値2^-900以上である間、フラッシュを行わない高速経路があります。この条件のもとで、零でない係数が全て絶対値2^-60以上であれば、1標本の中間値に非正規化数は現れず、フラッシュは何も変えません。零でない係数の最小値は、200 kHzまでの全ての整数の標本化周波数で測り、6.8e-7でした。入力と新しい状態の検査は標本ごとに行い、検査に外れた最初の標本と、状態が再び落ち着くまでのそれ以降の標本は、演算ごとにフラッシュする計算で処理します。音声が無音へ減衰した後は、状態が2^-900を下回ったままです。そのため、音声の後に続くデジタル無音は遅い経路に残り、そこではフィルタが最適化前の移植の1.6倍、全モードが2.1倍速く、雑音では3.5倍と5.6倍でした。

フィルタは、使われている隣り合う4チャネルを256ビットベクトルの群にし、次に隣り合う2チャネルを128ビットベクトルの群にして、残りを1チャネルずつ処理します。各レーンは原典と同じ順序で1チャネル分の演算を行うため、ビット単位で厳密です。LFEを未使用にした5.1のように未使用チャネルを含む配置でも、使われている隣り合う2チャネルごとに群を組みます。ゲーティングは原典のリングバッファの順序で標本をたどるため、各総和は1本の逐次の鎖のままであり、チャネルをレーンごとに並列に加算します。

サンプルピークは、チャネルの並びが3本のベクトルの中で繰り返される場合（1から4チャネル、6チャネル、8チャネル）に、インターリーブされた領域をそのままベクトル化します。最大値は取る順序に依存しないため結果はビット単位で厳密であり、比較は負のゼロと非数の扱いを含めて原典の三項演算を再現します。整数の入力は整数演算で扱い、最小の負数の絶対値は符号なしの数として表せます。それ以外のチャネル数では、絶対値を分岐なしに求めるスカラーのループを使います。

ループを含む計算核には`AggressiveOptimization`を付けています。実行時コンパイルでは、未最適化の階層から始めず、初回の呼び出しから最適化してコンパイルされます。Native AOTは事前にコンパイルするため影響を受けません。

## APIリファレンス

### 生成

```csharp
using R128Net;

using LoudnessMeter meter = new(channels: 2, sampleRate: 48000, LoudnessModes.All);
```

| メンバ | 説明 |
|---|---|
| `LoudnessMeter(int, int, LoudnessModes)` | 既定のオプションで測定器を生成します |
| `LoudnessMeter(int, int, LoudnessModes, in LoudnessMeterOptions)` | オプションを明示して測定器を生成します |
| `Channels`、`SampleRate`、`Modes` | 生成時に指定した構成 |
| `MaxWindowMilliseconds`、`MaxHistoryMilliseconds` | 現在の窓と履歴 |
| `FramesProcessed` | 生成後または直近の`Reset`以降に投入したフレーム数 |
| `Reset` | 構成を保ったまま測定を消去します |
| `SetMaxHistory(long)` | 保持する履歴を伸縮させます |
| `Dispose` | ネイティブ状態を解放します |

`LoudnessModes`は原典の含意関係を再現します。`ShortTerm`は`Momentary`を、`Integrated`は`Momentary`を、`LoudnessRange`は`ShortTerm`を、`TruePeak`は`SamplePeak`をそれぞれ含みます。

### 音声の投入

```csharp
meter.AddFrames(interleaved);
```

| オーバーロード | 全振幅値 |
|---|---|
| `AddFrames(ReadOnlySpan<short>)` | 32768 |
| `AddFrames(ReadOnlySpan<int>)` | 2147483648 |
| `AddFrames(ReadOnlySpan<float>)` | 1.0 |
| `AddFrames(ReadOnlySpan<double>)` | 1.0 |

標本はチャネル方向にインターリーブします。渡す領域はフレーム単位で割り切れる必要があります。

### ラウドネス

| メンバ | 単位 | 必要なモード |
|---|---|---|
| `MomentaryLoudness` | LUFS | `Momentary` |
| `ShortTermLoudness` | LUFS | `ShortTerm` |
| `IntegratedLoudness` | LUFS | `Integrated` |
| `LoudnessRange` | LU | `LoudnessRange` |
| `RelativeThreshold` | LUFS | `Integrated` |
| `GetLoudnessOverWindow(long)` | LUFS | `Momentary` |
| `LoudnessMeter.GatedLoudness(ReadOnlySpan<LoudnessMeter>)` | LUFS | 全ての測定器の`Integrated` |
| `LoudnessMeter.LoudnessRangeOf(ReadOnlySpan<LoudnessMeter>)` | LU | 全ての測定器の`LoudnessRange` |

ラウドネスが負の無限大となる場合は、素材が無音であるか、全体が絶対ゲートを下回っていることを意味します。ラウドネスレンジが0となる場合は、ゲートを通過した短期ブロックが不足していることを意味します。

### ピーク

| メンバ | 必要なモード |
|---|---|
| `GetSamplePeak(int)` | `SamplePeak` |
| `GetPreviousSamplePeak(int)` | `SamplePeak` |
| `GetTruePeak(int)` | `TruePeak` |
| `GetPreviousTruePeak(int)` | `TruePeak` |

1.0が0 dBFSに相当するため、デシベルへの換算は`20 * log10(値)`です。名前に`Previous`を含むものは直近の`AddFrames`に対する値を返します。トゥルーピークがサンプルピークを下回る値を返すことはありません。

### チャネル

| メンバ | 説明 |
|---|---|
| `SetChannel(int, ChannelPosition)` | チャネルへ位置を割り当てます |
| `GetChannel(int)` | チャネルの位置を読み出します |

既定の配置は、4チャネルと5チャネルにはBS.1770の配置を割り当て、それ以外は先頭から順に左、右、中央、未使用、左サラウンド、右サラウンドを割り当てます。`ChannelPosition.DualMono`はモノラルの測定器の単一チャネルにのみ指定できます。

### オプション

| メンバ | 既定値 | 説明 |
|---|---|---|
| `MaxWindowMilliseconds` | 0 | `GetLoudnessOverWindow`へ指定できる窓の上限。0は要求したモードが必要とする最小値を意味し、短期を含む場合は3000、含まない場合は400になります。フレーム数が収まらない窓と、400ミリ秒より少ないフレーム数へ巻き戻る窓は、`ArgumentOutOfRangeException`で拒否します |
| `MaxHistoryMilliseconds` | 4294967295 | 統合ラウドネスとラウドネスレンジが保持する履歴 |
| `PreallocateHistory` | `false` | 履歴を伸ばさず一度で寸法を決めます。`MaxHistoryMilliseconds`が既定のままだと生成時に約350 MBを確保するため、必要な長さの履歴を指定してください |
| `UseUpstreamWindowOverflow` | `false` | Windowsにおける原典の整数オーバフローを再現します |

## 制限事項

- MSVCでビルドしたlibebur128とのビット単位の一致は、.NETのランタイムと参照が同じ数学ライブラリを使うWindows x64で確認しています。
- CIはWindows ARM64、Linux x64、Linux ARM64でも、同じダンプに対してスイート全体を実行しています。プラットフォームの数学ライブラリを直接呼ぶ4件（`Math.Tan`、`Math.Log`、三角関数から作る補間器の係数とK特性の係数）を除く全ての比較が、そこでもビット単位で通ります。この4件は、これら3つのプラットフォームで、MSVCの実行時と特定の引数で最後の桁1つ分異なり、Windows ARM64の8000 HzのK特性の係数1つでは最大3つ分異なりました。そのため試験は、`Math.Tan`、`Math.Log`、補間器の係数に1つ分、K特性の係数に4つ分までの差を許します。したがって、別のプラットフォームでは、標本化周波数がそのような引数に当たると、測定値が最後の数桁で異なり得ます。ただし、スイートのラウドネスとピークの試験では起きませんでした。
- ヒストグラムの境界表は、1001個の要素のうち2個で、原典と最終位が1だけ異なります。埋め込んでいる値は正しく丸めた結果で、MSVCの`pow`は正しく丸めていません。IEEE 754は`pow`に正しい丸めを要求していません。違いはヒストグラムアルゴリズムの内部に限られます。
- `LoudnessMeter`はスレッドセーフではありません。並行して測定する場合はスレッドごとに測定器を用意してください。集約の機能はその用途のために設けています。
- 前置フィルタが発散する標本化周波数は、原典が受理するのに対し、本実装は生成時に拒否します。3364 Hz以上は全て受理します。
- `ebur128_set_max_window`の代わりに`LoudnessMeterOptions.MaxWindowMilliseconds`を使います。測定の途中で確保し直すのではなく、生成時に寸法を確定させます。`ebur128_change_parameters`は移植していません。全てのバッファを確保し直して測定を破棄する関数で、測定器を作り直すことと変わらないうえ、原典の実装は上記の整数オーバフローを抱えているためです。
- `MaxWindowMilliseconds`をモードの既定より大きくすると、環状バッファが巻き戻る頻度が変わります。原典の総和は巻き戻したブロックの二つの区間を、巻き戻していない場合と逆の順序でたどるため、ゲートを通る測定値が最終位の数単位分ずれます。ステレオ12秒の測定では4単位分でした。ピークは影響を受けず、既定の窓は原典を厳密に再現します。
- 比較のテストには参照データが必要です。`reference/data`が存在しない場合、それらのテストは実行できません。
- `R128Net.Examples`配下の実行例はコンソールへ出力するためマネージドヒープを確保します。無確保の保証はライブラリに対するものです。

## 注意事項

- 処理の費用: トゥルーピークが最も高価であり、上のステレオの計測では全体の約5分の2を占めます。モードの集合から外すことが測定を速くする最も効果的な手段です。サンプルピークとゲーティングはこれに比べて小さい費用です。
- アーキテクチャをまたぐ非正規化数の扱い: 原典のソースでは、フラッシュトゥゼロのビットを有効にするのはSSE2を使う場合だけで、それ以外では呼び出しごとに1回、状態を手作業でフラッシュします。これは非正規化数の値で結果が変わります。本移植はx86-64の動作をどのアーキテクチャでも再現するため、結果はどれでも同一であり、x86-64で作ったダンプとの一致をスイートが確かめています。ほかのアーキテクチャで原典をネイティブにビルドしたものとは、非正規化数の値に限って異なり得ます。これはソースを読んで導いたもので、そのようなビルドとの比較はしていません。
- 非正規化数の扱い: 原典はフィルタ処理の間、MXCSRレジスタのフラッシュトゥゼロビットを有効にします。.NETのランタイムは相当する機能を公開していないため、演算単位でフラッシュを模倣し、恒等になると証明できる演算では省いています。この模倣は無音時の減衰における状態の遷移を原典と厳密に再現し、加えて、非正規化数の演算が無音時に招く50倍の速度低下も回避します。
- 測定器の再利用: 状態は生成時に一度だけ確保します。バッファごとに測定器を作ると、一度だけ確保する意味がなくなり、ネイティブ領域の確保が再び生じます。候補の切り替えでは`Reset`を呼んでください。構成に触れず、確保も伴わずに測定だけを消去します。
- 決定性: 測定は繰り返しても同一の結果を生み、`AddFrames`へ渡すバッファの長さにも依存しません。テストは同じ素材を1フレームずつ投入した場合と一括で投入した場合の結果をビット単位で比較しています。
- 状態の配置: `[StateLayout]`を付けた型は、`IStateAllocator`を型引数に取るジェネリックな`Layout`メソッドを公開する必要があります。ジェネレータは対応する引数列を持つ`GetRequiredBytes`と`Bind`を生成し、型が既に宣言している方は生成しません。
- Native AOT: ライブラリは`IsAotCompatible`を指定しており、トリムと単一ファイルとAOTの各アナライザが有効になります。`publish-aot.bat`は実行例を`win-x64`向けに発行し、ネイティブリンカのためMSVCツールセットを必要とします。加えてVisual Studioのインストーラのディレクトリを検索パスへ追加します。`vswhere.exe`を解決できない場合、AOTコンパイラのリンカ探索が失敗するためです。
- 参照データの再生成: `reference/build.bat`はlibebur128を`reference/ebur128-src`へ取得し、固定したコミットであることを検証してからビルドし、データを書き出します。取得先とビルド生成物はバージョン管理から除外しています。
